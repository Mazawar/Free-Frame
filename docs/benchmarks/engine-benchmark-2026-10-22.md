# 引擎吞吐边界压测报告(2026-10-22)

**对象**:`netproto-core` StackDecoder / StackEncoder + demo 三套业务协议(pd 9000 / dev 9001 / iot 9002),注册表 49 个协议,根协议 ethernet。

**方法**:手写 harness(`netproto-demo/src/test/java/com/netproto/demo/bench/EngineBench.java`),非 JMH。每场景预热 2 轮 + 测量 8 轮(各 1s),取峰值轮;blackhole 累计防死码消除。共跑 3 次(4/4/8 轮),报告取多轮一致的峰值,波动大的给区间。

**环境**:JDK 25(G1,默认参数)/ Intel 12 代 20 逻辑核(P+E 混合,笔记本)/ Windows 11 / 后台有常驻服务。混合核 + 后台负载导致运行间波动可达 2x,表中数值为多轮一致的峰值(乐观界)。

复现:`./mvnw -pl netproto-demo org.codehaus.mojo:exec-maven-plugin:3.2.0:java -Dexec.mainClass=com.netproto.demo.bench.EngineBench -Dexec.classpathScope=test -Dbench.rounds=8`

## 结论:边界在哪

1. **引擎是"帧率受限"而非"带宽受限"**:小帧(64B)15–18 万帧/s ≈ **百兆线速(14.88 万 pps)边界**;大帧 2.5–3.3 GB/s 超 20GbE 带宽。千兆小帧线速(148 万 pps)差 8–10 倍,是当前架构的数量级天花板。
2. **每注册层 ~1–1.4µs**:5 层栈 5.4–6.7µs。成本构成:每层两个 LinkedHashMap 位区间簿记 + matchChild 条件求值 + 反射字段 setAccessible。未注册层的 payload 只引用不拷贝,但 @Payload 提取拷贝 ~3 GB/s 封顶(60KB 帧带宽界)。
3. **列表线性扩展**:计数列表每条目解码 ~0.5–0.7µs、编码 ~0.9µs,无超线性退化。
4. **畸形帧健壮**:58 种截断前缀全部安全停下(逐层 try/catch),成本与正常帧同量级甚至更快(提前终止)。
5. **并发既不安全也不扩展**:`ProtocolCodec.lastFieldRanges` 是 codec 单例上的可变 HashMap(源码注释自述"分派线程内单线程使用"),`StackDecoder` 解码后立即读它 → 多线程解码海量 ConcurrentModificationException;吞吐 4 线程封顶 ~2.5x,8 线程起负增长。**当前安全模型 = 单线程采集管道**(现网 CaptureEngine 正是单线程,故线上无恙)。

## 若要提吞吐(按性价比)

1. `lastFieldRanges` 改为解码返回值携带或 ThreadLocal 化 → 同时解决线程安全与并发扩展;
2. 位区间簿记惰性化(仅 UI 选帧时重算)→ 预计砍掉每层约一半对象分配;
3. `Field`/`setAccessible` 构造期一次性缓存(编码侧 `findFieldByName` 每次序列化都线性扫描 getDeclaredFields);
4. 需要千兆小帧线速时:按 CPU 栈分片并行(先做 1),或对热路径协议提供生成代码快路径。

## 与引擎加固缺口的关系

本次压测实证了自审清单中的并发缺口(lastFieldRanges);越界/溢出类缺口在畸形帧全扫中未触发崩溃(逐层 try/catch 兜底),但"截断帧静默降层"在 UI 上表现为帧层数变少,属可接受行为。

# 优化后复测(同日,第一轮优化)

优化内容(全在 netproto-core,行为不变、160 测试全绿):
1. `ProtocolCodec` 解码状态(lastFieldRanges/lastHeaderBits/layerEndBits)实例字段 → **ThreadLocal**;
2. 反射一次性就绪:无参构造器、字段、计数字段 setAccessible 构造期完成(此前每字段每帧都调);
3. LIST 解码**零拷贝**:`(bytes, offset, len)` 直读 + `lastConsumedBits()` 步进,替代「整段拷贝 + 反向序列化测长」;
4. `ProtocolRegistry.byType` O(1) 查表;`autoWireAssignments` 构造期解析缓存(此前每次编码重新解析 when 字符串);`contextOf` 注解字段按类缓存;
5. `StackEncoder` payload/选择子字段按类缓存。

## 优化后结论

1. **并发解码从"不安全+4线程封顶"变为线程安全且近线性扩展**:16 线程 96 万帧/秒(9.3x),ConcurrentModificationException 清零。
2. **编码反超解码**:小帧编码 36–46 万帧/秒(此前 10 万),瓶颈从反射开销移回真正的字节组装。
3. **列表解码 3–8 倍**:零拷贝 + 消费位数直读,1000 条目帧从 695µs 降到 86µs(178 MB/s)。
4. **新边界**:单线程小帧 15–21 万帧/秒(略超百兆线速);16 线程 96 万帧/秒 ≈ 千兆小帧线速的 65%。距千兆线速的剩余差距在每层 1µs 的位区间簿记与表达式分派(下一轮优化点:位区间惰性化)。
5. 编码侧大列表(iot 1000 条)未提速:序列化每个元素本就要真实做功,属合理成本。

# 第二轮优化复测(同日)

优化内容:
1. **BitCursor 读写逐字节取块**:readBits/peekBits/writeBits 原为逐位循环(每字段每 bit 一次移位+掩码),改为按字节分块;readBytes 对齐场景走 System.arraycopy。微基准:48 位读写 12M/24M → 76M/88M ops/s(**3–6 倍**)。
2. **位区间惰性化**:采集热路径 `decode(..., wantRanges=false)` 关闭每字段 int[2]+HashMap 写入与每层两组 LinkedHashMap(UI 详情由 `detail()` 按需重解码补全,采集路径的区间数据本就无人消费);开关只作用于实际访问的层(初版误做全注册表扫描,已修)。
3. 基准的解码/并发场景改走采集快路径,新增 `detail-path` 场景对照(含位区间)。

## 二轮后边界结论

- **16 线程聚合 156 万帧/秒,超过千兆以太网 64B 小帧线速(148.8 万 pps)**——引擎吞吐不再是被压测链路里最先到顶的组件。
- 单线程:解码 26–32 万帧/秒(约为千兆线速 20%)、编码 50–61 万帧/秒、大帧 3.7 GB/s。
- 单层地板(eth-only)1.4–1.5M:快路径为跟踪开关引入少量固定开销,对 3 字段小层略亏,对真实 5 层栈整体大赚。
- 剩余可优化项(性价比递减):编码 LIST 双遍序列化(算总位+写入各序列化一次,可减半)、matchChild 每层建 FieldContext、DecodedLayer 固定对象头。

# 第三轮优化复测(同日)

优化内容:编码两遍循环的元素字节复用——`serialize` 增加 per-call scratch 缓存,第一遍(算总位数)序列化的 LIST/TLV/sentinel-LIST/动态 NESTED 元素字节,第二遍(写入)直接复用;此前两遍各序列化一次,大列表编码白做一半功。附带:readSentinelValue 的 LIST 解码同享零拷贝步进(压测中发现的第 5 处同类浪费)。

matchChild 的 FieldContext 优化经评估**放弃**:lenient 分派模式依赖"字段未解析"判据(UnknownIdentifier),改成直读反射会破坏该语义,风险大于收益。

| 维度 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
